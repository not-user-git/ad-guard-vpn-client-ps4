# 1. Описание проекта

## 1.1. Цель

Разработать нативный VPN-клиент для PlayStation 4, позволяющий подключаться к коммерческой инфраструктуре AdGuard VPN непосредственно с консоли.

Приложение должно работать в окружении GoldHEN и распространяться в формате PKG.

Основной сценарий использования — маршрутизация сетевого трафика выбранных игр через VPN-серверы AdGuard с сохранением прямого подключения для остальных системных компонентов PS4.

Проект не предполагает создание собственной VPN-инфраструктуры. Используются существующие коммерческие серверы AdGuard VPN и официально предоставляемые механизмы подключения.

## 1.2. Основные задачи

1. Исследовать сетевую подсистему Orbis OS.
    
2. Определить доступные способы реализации VPN на PS4.
    
3. Исследовать совместимость IPsec/IKEv2 с инфраструктурой AdGuard VPN.
    
4. Изучить возможность использования TrustTunnel.
    
5. Реализовать VPN Engine.
    
6. Реализовать выборочную маршрутизацию игрового трафика.
    
7. Интегрировать системный компонент с GoldHEN.
    
8. Разработать графический интерфейс.
    
9. Реализовать управление VPN-подключением.
    
10. Обеспечить стабильность, безопасность и производительность.

|FR-13|Настройки сетевого соединения|Medium|

## 2.2. Режим маршрутизации

Основной режим — `Selected Games Only`.

Поведение:

- Игры из списка направляются через VPN.
    
- Системный трафик по умолчанию использует обычное подключение.
    
- Трафик самого VPN-туннеля всегда использует физическое сетевое подключение.
    
- При потере VPN выбранный игровой трафик блокируется, если активирован Kill Switch.
    
- После восстановления соединения маршрутизация возвращается в рабочее состояние.
    

Дополнительные режимы в будущем:

- Full Tunnel — весь трафик через VPN.
    
- Direct — обычное подключение.  

## 2.3. Идентификация игр

Для идентификации игр предполагается использовать Title ID.

Пример:

```
{
  "routing": {
    "mode": "selected_games",
    "default": "direct",
    "kill_switch": true
  },
  "games": [
    {
      "title_id": "CUSA00001",
      "enabled": true
    },
    {
      "title_id": "CUSA00002",
      "enabled": false
    }
  ]
}
```

Title ID определяет игру, но сам по себе не обеспечивает идентификацию владельца каждого сетевого пакета.

Для этого необходимо исследовать механизмы связи процессов, сокетов и сетевого стека Orbis OS.

# 3. Ограничения платформы

## 3.1. PlayStation 4

Платформа использует собственную операционную систему Orbis OS.

Она не является обычным Linux-дистрибутивом, несмотря на родственные архитектурные особенности.

Необходимо учитывать:

- Ограниченную доступность системных API.
    
- Отсутствие гарантированной поддержки стандартных Linux-интерфейсов.
    
- Особенности ABI и системных библиотек.
    
- Ограничения доступа к сетевому стеку.
    
- Ограничения выполнения фоновых компонентов.
    
- Особенности работы Homebrew-приложений.
    
- Совместимость с конкретными версиями прошивки.
    

## 3.2. GoldHEN

GoldHEN используется для запуска Homebrew и загрузки дополнительных компонентов.

Предполагаемые возможности:

- Запуск PKG.
    
- Загрузка PRX-плагинов.
    
- Взаимодействие с системными функциями.
    
- Работа с процессами и игровыми приложениями.
    

Наличие GoldHEN не гарантирует возможность полноценного перехвата IP-пакетов или изменения системной маршрутизации.

Эти возможности должны быть проверены экспериментально.

## 3.3. Главные технические ограничения

1. Отсутствие подтверждённого стандартного TUN API.
    
2. Неизвестная доступность низкоуровневого packet I/O.
    
3. Необходимость адаптации VPN Engine.
    
4. Ограничения работы фоновых PRX.
    
5. Необходимость определения принадлежности сокетов процессам.
    
6. Необходимость проверки доступности криптографических примитивов.

# 4. Коммерческая инфраструктура AdGuard VPN

## 4.1. Принципиальное решение

Проект должен использовать существующую коммерческую инфраструктуру AdGuard VPN.

Создание собственных серверов не входит в основной объём работ.

Необходимо отдельно исследовать доступные механизмы подключения сторонних устройств.

## 4.2. IPsec / IKEv2

Первый кандидат для реализации.

AdGuard предоставляет механизм добавления роутера через личный кабинет.

Предполагаемый процесс:

1. Пользователь авторизуется в AdGuard.
    
2. Переходит в раздел управления устройствами.
    
3. Добавляет роутер.
    
4. Выбирает доступную локацию.
    
5. Получает параметры подключения.
    
6. Использует полученные credentials в PS4-клиенте.
    

Необходимо выяснить:

- Какие версии IKE поддерживаются.
    
- Какие методы аутентификации используются.
    
- Какие алгоритмы шифрования поддерживаются.
    
- Используется ли EAP, PSK или другой механизм.
    
- Какие параметры ESP согласуются.
    
- Поддерживается ли NAT Traversal.
    
- Какие порты и протоколы необходимы.
    
- Как осуществляется смена ключей.
    
- Какие ограничения существуют у router credentials.
    

Нельзя считать совместимость подтверждённой до успешного подключения с PS4.

## 4.3. TrustTunnel

Второй кандидат.

TrustTunnel — открытый VPN-протокол, развиваемый AdGuard.

Исходный код:

[https://github.com/TrustTunnel/TrustTunnel](https://github.com/TrustTunnel/TrustTunnel)

Необходимо исследовать:

- Архитектуру протокола.
    
- Клиентскую реализацию.
    
- Систему авторизации.
    
- Формат конфигураций.
    
- HTTP/2 transport.
    
- HTTP/3 transport.
    
- QUIC.
    
- Механизм передачи IP-пакетов.
    
- Требования к сетевому интерфейсу.
    
- Зависимости от платформы.
    

Критическое ограничение:

Открытость TrustTunnel не означает, что коммерческие серверы AdGuard принимают произвольные сторонние подключения.

Необходимо получить официальное подтверждение совместимости с коммерческой инфраструктурой.

## 4.4. AdGuard VPN CLI

Репозиторий:

[https://github.com/AdguardTeam/AdGuardVPNCLI](https://github.com/AdguardTeam/AdGuardVPNCLI)

CLI необходимо изучить как источник информации о:

- Авторизации.
    
- Получении списка серверов.
    
- Выборе локаций.
    
- Управлении подключением.
    
- Форматах конфигураций.
    
- Поддерживаемых протоколах.
    

Исходный код коммерческого клиента не следует считать доступным только на основании наличия публичного GitHub-репозитория.

Необходимо соблюдать официальные условия использования и не закладывать зависимость от недокументированных приватных API.

## 4.5. Приоритет протоколов

|Протокол|Приоритет|Обоснование|
|---|---|---|
|IPsec / IKEv2|P0|Документированный способ подключения роутера|
|TrustTunnel|P1|Открытый протокол AdGuard|
|WireGuard|P3|Не является подтверждённым способом подключения к коммерческим серверам AdGuard|

Ответственность:

- Выбор сервера.
    
- Управление подключением.

## 5.3. Core

Центральный слой приложения.

Ответственность:

## 5.4. VPN Engine

Назначение: реализация защищённого VPN-соединения.

Ответственность:

- Установка соединения.
    
- Аутентификация.
    
- Согласование криптографических параметров.
    
- Шифрование и расшифровка.
    
- Передача пакетов.
    
- NAT Traversal.
    
- Rekeying.
    
- Обработка потери соединения.
    

Предполагаемая технология:

- IPsec / IKEv2.
    
- Проверенные криптографические библиотеки.
    
- Возможное использование компонентов strongSwan.
    

strongSwan:

[https://github.com/strongswan/strongswan](https://github.com/strongswan/strongswan)

Необходимо проверить возможность портирования его компонентов и зависимостей под Orbis OS.

## 5.5. Traffic Router

Назначение: выборочная маршрутизация сетевого трафика.

Ответственность:

- Идентификация игровых процессов.
    
- Определение владельцев сокетов.
    
- Отбор сетевых пакетов.
    
- Перенаправление трафика в VPN.
    
- Обработка обратного трафика.
    
- Исключение VPN endpoint.
    
- Kill Switch.
    

Предпочтительный язык: C.

Предполагаемая интеграция: GoldHEN PRX.

## 5.6. IPC

Необходимо организовать взаимодействие между приложением, VPN Engine и GoldHEN PRX.

Предполагаемые команды:

```
CONNECT
DISCONNECT
GET_STATUS
GET_STATISTICS
SET_ROUTING_RULES
ADD_GAME
REMOVE_GAME
ENABLE_KILL_SWITCH
DISABLE_KILL_SWITCH
```

Конкретный IPC-механизм выбирается после исследования доступных возможностей Orbis OS.

# 8. Архитектурные принципы

## 8.1. Разделение ответственности

Каждый компонент должен иметь одну основную ответственность.

UI не должен напрямую управлять сетевыми сокетами.

VPN Engine не должен содержать бизнес-логику пользовательского интерфейса.

Traffic Router не должен зависеть от визуального слоя.

## 8.2. Модульность

VPN Engine должен иметь абстракцию транспорта.

Предполагаемая структура:

```
class IVpnEngine {
public:
    virtual bool connect() = 0;
    virtual void disconnect() = 0;
    virtual bool isConnected() const = 0;
    virtual ~IVpnEngine() = default;
};
```

Это позволит в будущем добавлять другие протоколы без изменения основного приложения.

## 8.3. Отказоустойчивость

- Потеря VPN не должна приводить к утечке игрового трафика при включённом Kill Switch.
    
- Ошибка UI не должна автоматически отключать VPN.
    
- Ошибка VPN Engine должна корректно обрабатываться Core.
    
- Повторное подключение не должно создавать дублирующие туннели.
    
- Системный трафик не должен случайно попадать в VPN.
    

## 8.4. Безопасность

- Credentials не хранятся в открытом виде без необходимости.
    
- Приватные данные не попадают в логи.
    
- Не использовать самописную криптографию.
    
- Проверять сертификаты и криптографические параметры.
    
- Использовать только документированные механизмы доступа к коммерческой инфраструктуре.

- Невозможно реализовать необходимый packet I/O.
    
- Невозможно получить совместимые параметры подключения AdGuard.
    
- Невозможно обеспечить обратную маршрутизацию.
    
- Невозможно безопасно реализовать Kill Switch.
    
- Невозможно идентифицировать игровой трафик с приемлемой надёжностью.
    

В таких случаях необходимо оценить альтернативные механизмы на уровне GoldHEN или отдельного сетевого оборудования, не выдавая их за нативный VPN.
